NEW → CONFIRMED → ACTIVE → TEMPORARILY_LOST → RECOVERED → EXITED

Trajectory History

Yes — this is actually the most important part. A lot of people can make YOLO → tracker → database; the difficult part is building the engineering logic around imperfect computer vision.

For your project, I'd specifically protect against these mistakes:

1. Don't treat detection = person

A detector says:

"I see something that looks like a person."

It does not say:

"This is Person P104."

You need separate concepts:

Detection → Track → Global Identity → Event

2. Never trust a single frame

Bad:

person detected
→ immediately create ID
→ immediately count

Better:

Detection
 ↓
Temporal confirmation
 ↓
Track established
 ↓
Global identity assigned
 ↓
Event validated
 ↓
Count

This alone eliminates a huge amount of flickering.

3. Never delete an ID immediately

This is one of the biggest mistakes.

Person disappears for 0.5–2 seconds:

WRONG

ID 17 disappeared
→ delete ID 17
→ new person detected
→ create ID 32

BETTER

ID 17 lost
 ↓
prediction
 ↓
short-term memory
 ↓
search nearby detections
 ↓
Re-ID
 ↓
trajectory validation
 ↓
recover ID 17
4. Separate LOCAL ID and GLOBAL ID

This is critical.

Tracker:
ID 17

doesn't mean:

Real person:
P000381

Your architecture should have:

Camera Track ID
       ↓
Global Identity Manager
       ↓
Global Person ID

That protects you from tracker ID recycling.

5. Never count based on presence

Don't do:

Person detected inside entrance
→ +1

Do:

Outside
   ↓
approaches entry line
   ↓
crosses line
   ↓
direction verified
   ↓
track confirmed
   ↓
not previously counted
   ↓
ENTRY EVENT
   ↓
+1
6. Make IN/OUT a state machine

For example:

UNKNOWN
   ↓
OUTSIDE
   ↓
APPROACHING_ENTRY
   ↓
CROSSED_IN
   ↓
INSIDE
   ↓
APPROACHING_EXIT
   ↓
CROSSED_OUT
   ↓
OUTSIDE

Now someone standing on the line for 30 seconds doesn't generate 20 entries.

7. Don't confuse re-entry with a new person

This is exactly what you described.

Example:

P0042
IN 10:00
OUT 11:00
IN 11:20
OUT 12:00

That's:

1 unique person

but:

2 visits

You should store both concepts separately.

Unique People = 1
Visits = 2
8. Staff must be a separate population

Don't do:

person detected
→ customer count

Instead:

PERSON
 ├── STAFF
 │    └── Staff ID
 │
 └── CUSTOMER
      └── Anonymous Global ID

Staff should be excluded from customer IN/OUT automatically.

9. Don't use Re-ID as absolute truth

Re-ID can be wrong.

Even if:

similarity = 0.94

don't blindly say:

SAME PERSON.

Combine:

Re-ID
+
trajectory
+
time
+
position
+
zone
+
motion

Example:

If Re-ID says same person but the person would have needed to travel 30 meters in 0.2 seconds, reject it.

That's engineering logic, not just ML.

10. Add impossible-movement checks

This is incredibly valuable.

If:

t = 10:00:01
Position = Reception

and:

t = 10:00:01.2
Position = Dining

but the physical distance requires 3 seconds to travel:

something is wrong.

Flag the identity association.

11. Track confidence separately from detection confidence

Don't make:

YOLO confidence = 95%

mean:

Person identity confidence = 95%

Have separate scores:

Detection confidence
Tracking confidence
Re-ID confidence
Zone confidence
Direction confidence
Identity confidence
Event confidence

Then calculate an overall event confidence.

12. Use hysteresis

This is extremely useful for zone boundaries.

Instead of:

inside
outside
inside
outside
inside

when someone is standing near a boundary:

Require the person to remain sufficiently inside/outside for a short temporal window.

This prevents zone flickering.

13. Don't run expensive models everywhere

Your pipeline should have a compute budget.

For example:

Every frame
    ↓
Tracker


Every N frames
    ↓
YOLO


Only uncertain tracks
    ↓
Re-ID


Only important tracks
    ↓
Pose


Only relevant events
    ↓
Action recognition

This is how you get speed without destroying accuracy.

14. Don't let the database slow the CV pipeline

Bad:

Frame
→ inference
→ database INSERT
→ next frame

Better:

CV Pipeline
    ↓
Event Queue
    ↓
Database Worker

The video pipeline should never wait for PostgreSQL.

15. Store raw evidence, not just conclusions

Don't store only:

P0042 entered at 10:31

Store:

Person ID
Timestamp
Camera
Zone
Direction
Track confidence
Identity confidence
Event confidence
Bounding box
Trajectory
Best frame
Evidence clip

Then when someone says:

"Why did the AI count this person?"

you can actually prove it.

16. Build an "uncertain" category

This is very important if you want high accuracy.

Don't force the model to answer:

YES / NO

Give it:

CONFIRMED
PROBABLE
UNCERTAIN
REJECTED

For example:

Identity:
P0042 — 97% → CONFIRMED


Identity:
P0081 — 71% → PROBABLE


Identity:
P0192 — 43% → UNCERTAIN

Then your dashboard can say:

2,438 confirmed events

17 events require review

instead of quietly producing a wrong number.

17. Build replay/debugging from Day 1

This is something many ML projects completely miss.

Every decision should be reproducible:

Video
 ↓
Frame
 ↓
Detection
 ↓
Track
 ↓
Re-ID
 ↓
Zone
 ↓
Event

You should be able to click:

Event #18291

and see:

Frame before
Frame during
Frame after
Track trajectory
Re-ID candidates
Confidence scores
Decision reason

That will make debugging your system 10× easier.

And one final engineering principle:

Don't build a system that assumes the AI is always right. Build a system that knows when the AI might be wrong.

Yes. If you're serious about turning this into a robust venue-surveillance system, there are a few more things I'd add. These are the things people usually realize after their first real deployment.

🔴 Highest priority
Camera health monitoring
Detect camera offline/frozen feed.
Detect black screen, extreme darkness, overexposure.
Detect camera movement or changed angle.
Detect lens obstruction/blur.
If calibration becomes invalid, stop trusting counts.

Scene-change detection

Furniture moved?
Reception desk moved?
New obstacle?
Camera angle changed?

Your zones and homography can become invalid without the ML model actually failing.

Occlusion reasoning
Track people differently when:

partially blocked
completely blocked temporarily
behind reception desk
inside a crowd

Don't immediately terminate tracks.

Tracklet stitching

Instead of thinking only frame-by-frame:

Track 17 → Track 31

maintain tracklets and later determine:

Tracklet A + Tracklet B = Global Person P104

This is extremely useful for long videos.

Cross-camera identity architecture—even if you only have one camera today

Design your database as:

Camera → Local Track → Global Person

Then if you add Camera 2 later, you don't have to redesign everything.

🟠 Very useful

Time synchronization

Every event should use a proper timestamp and consistent timezone.

Especially important when eventually combining multiple cameras.

Frame sampling strategy

Don't blindly process every frame.

Use adaptive processing:

Static scene → low inference

Crowd → higher inference

Fast movement → higher inference

Stable track → tracker only

Crowd mode

Your normal tracking logic may work beautifully for 1–5 people and fall apart with 30 people.

Detect crowd density and automatically change:

detector frequency
Re-ID frequency
confidence thresholds
tracking parameters

Camera-specific configuration

Don't hard-code one global configuration.

Each camera should have:

zones
lines
expected direction
perspective parameters
detection thresholds
night parameters
staff gallery
calibration version
Version everything

Store:

model_version

tracker_version

calibration_version

pipeline_version

with each event.

Otherwise, after changing your model, you won't know why yesterday's count differs from today's.

🟡 A feature I'd REALLY recommend
Confidence-driven processing

Instead of processing everything equally:

HIGH CONFIDENCE
     ↓
Normal tracking
     ↓
Cheap




MEDIUM CONFIDENCE
     ↓
More frames
     ↓
Re-ID




LOW CONFIDENCE
     ↓
Pose + Re-ID + trajectory
     ↓
Evidence clip
     ↓
Human review if necessary

That gives you speed where you can afford it and accuracy where it matters.

This is probably one of the most important architectural ideas for your project.

Separate:

What the model sees
Detection

Track

Pose

from:

What the system concludes

Don't directly turn a YOLO detection into a business event.

Use:

Every event should have a reason.

For example:

P102 counted as IN

Because:

✓ Track stable for 3.4 sec
✓ Entry line crossed
✓ Direction = outside → inside
✓ Re-ID consistent
✓ Zone transition valid
✓ Not previously counted for this visit
✓ Event confidence = 96%

If something goes wrong, you immediately know which layer failed.

Create a proper test dataset with difficult situations:

And track metrics such as:

🚨 One thing I would NOT do

Don't start by building everything:

YOLO + Re-ID + Pose + Action Recognition + Anomaly AI + DeepStream + database + dashboard + etc.

You'll end up with 15 components and no idea which one is causing the error.

Build in this order:

Phase 1

Detection → Tracking → stable IDs

Phase 2

Global identity → Re-ID → track recovery

Phase 3

Zones → line crossing → unique IN/OUT

Phase 4

Staff identity → staff activity

Phase 5

Motion → day/night → adaptive inference

Phase 6

Pose → action recognition

Phase 7

Anomalies → evidence → review system

Phase 8

DeepStream/TensorRT optimization → 24-hour production deployment

That way, every phase has a measurable accuracy target.

The ultimate goal

Don't think of this as a "YOLO project."

Think of it as a:

Persistent Video Intelligence + Event Reasoning System

The detector is just one sensor feeding that system.

And honestly, persistent identity + temporal reasoning + event/state machines + uncertainty handling + evidence/replay are where I'd spend most of your engineering effort. That's where your system can become genuinely strong rather than just another people-counter.
